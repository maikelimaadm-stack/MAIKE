# P4.0-R2 — Base URL nativa com esquema obrigatório

**Decisão:** D-PROD-26 · **Gate:** `P4-NATIVE-SCHEME` (em `gate:native-api`)

Fatia **corretiva da P4.0**, não uma fatia nova de migração: o defeito está no
transporte que a P4.0 entregou. `P4.2` continua reservada para `AreaPastagem
Native Persistence` no ROADMAP.

Diferente de todas as fatias anteriores da P4, esta não saiu de análise de
código: saiu de um defeito que chegou ao usuário em produção, com o aplicativo
publicado e o backend no ar.

---

## 1. O sintoma

O login não funcionava na Vercel. A tela aceitava cliente, usuário e senha e
devolvia erro genérico.

Ao mesmo tempo, o backend estava perfeitamente saudável:

| Verificação | Resultado |
|---|---|
| `GET /health` | `200` · `{"status":"ok","processo":"up","banco":"up"}` |
| `POST /auth/login` com a senha certa | `200` + JWT |
| `POST /auth/login` com senha errada | `401 AUTH_INVALID_CREDENTIALS` |
| `GET /auth/contexto` com Bearer | `200` |
| `GET /auth/contexto` sem token | `401 TENANT_CONTEXT_REQUIRED` |
| CORS preflight de `https://maike-five.vercel.app` | `204` + `access-control-allow-origin` |
| CORS preflight de `https://maike-five.vercel.app.evil.com` | `404`, **sem** header |

Sete provas verdes, incluindo dois controles negativos. Nenhuma delas tocava no
defeito, porque **todas usavam `curl`**.

## 2. A causa

O bundle publicado carregava:

```js
H0e = () => { try { return eN("maike-production.up.railway.app") } catch { return null } }
```

`VITE_MAIKE_API_URL` fora configurada **sem esquema**. E
`src/apis/_core/nativeHttpClient.js` monta a URL por concatenação literal:

```js
const montarUrl = (base, caminho) => `${base}${caminho.startsWith('/') ? caminho : `/${caminho}`}`;
```

`fetch('maike-production.up.railway.app/auth/login')` não é erro: é uma URL
**relativa**. O navegador a resolveu contra a origem do documento. Confirmado
chamando exatamente o que o navegador chamava:

```
POST https://maike-five.vercel.app/maike-production.up.railway.app/auth/login
→ HTTP 404 · content-type: text/plain · "The page could not be found"
```

O corpo não era JSON, `lerCorpo` devolveu `null`, a validação do retorno falhou
e virou `OPERATION_FAILED` na tela.

## 3. Por que isso é mais grave do que "login quebrado"

O corpo do `POST /auth/login` carrega `cliente`, `login` e **`senha` em texto**.
Durante todo o período do defeito, cada tentativa de login mandou a credencial
para a **origem do frontend**, não para o backend.

Não houve indisponibilidade — houve credencial entregue ao host errado, em
silêncio, sem nenhum sinal na tela ou no console que apontasse para o destino.

O `credentials: 'omit'` da P4.0 não ajuda aqui: ele governa cookie, e a senha ia
no corpo.

## 4. Por que nenhum gate pegou

O `gate:native-api` da P4.0 já cobria a variável — mas cobria a **procedência**
dela, não a **forma**:

- `P4-NATIVE-CONFIG` exige referência estática (`import.meta.env.VITE_MAIKE_API_URL`),
  proíbe override por query string ou storage, e exige documentação no
  `.env.example`. Tudo isso continuava verdadeiro com o valor errado;
- `P4-NATIVE-HTTP-BOUNDARY` exige que só a fronteira consuma a base. Também
  continuava verdadeiro.

O caminho **ausente** falhava bem desde a P4.0: `getNativeApiUrl()` devolvia
`null` e `nativeRequest` lançava `PROVIDER_UNAVAILABLE` sem tocar na rede — com
um comentário que explicava exatamente o risco:

> Sem URL configurada não existe "tentar assim mesmo": chamar caminho relativo
> bateria no host do frontend e devolveria o `index.html` […]

O buraco era o valor **presente e malformado**. A P4.0 previu o vazio e não
previu o inválido.

## 5. A correção

`src/config/runtimeConfig.js`:

```js
const HOST_PURO = /^[a-zA-Z0-9][a-zA-Z0-9.-]*(:\d{1,5})?$/;

const comEsquemaExplicito = (url) => {
  if (typeof url !== 'string' || url === '') return null;
  if (/^https?:\/\//.test(url)) return url;
  return HOST_PURO.test(url) ? `https://${url}` : null;
};

export const getNativeApiUrl = () => comEsquemaExplicito(semBarraFinal(lerMaikeApiUrl()));
```

| Entrada | Saída |
|---|---|
| `https://api.exemplo.com` | intacta |
| `http://localhost:3333` | intacta |
| `api.exemplo.com` | `https://api.exemplo.com` |
| `api.exemplo.com:8443` | `https://api.exemplo.com:8443` |
| `//outro.host` | `null` |
| `javascript:alert(1)` | `null` |
| `ftp://api.exemplo.com` | `null` |
| `/api` | `null` |
| `api.exemplo.com/api` | `null` |

O raciocínio sobre normalizar em vez de recusar tudo está em D-PROD-26.
Resumo: `VITE_*` é variável de **build**, então recusar o host puro custaria um
deploy inteiro de indisponibilidade por uma configuração que tem exatamente uma
leitura segura. O que não é aceito é toda forma **ambígua** — e são justamente
essas que produziriam requisição same-origin ou destino inesperado.

`new URL()` continua fora, pelo motivo já registrado em D-PROD-24:
`new URL('javascript:alert(1)')` é válida para o construtor.

## 6. Gate e provas

`P4-NATIVE-SCHEME`, absoluto, sem baseline, sem `--update`. Exige as **duas
pontas**, porque proteger só uma seria decorativo:

| Prova | Mutilação | Esperado |
|---|---|---|
| NAT-25 | `getNativeApiUrl` volta a não chamar `comEsquemaExplicito` | reprova |
| NAT-26 | a definição de `comEsquemaExplicito` é renomeada | reprova |
| NAT-27 | o corpo vira `return url`, mantendo nome e chamada | reprova |
| NAT-28 | **controle positivo**: o repositório real passa e não emite `P4-NATIVE-SCHEME` | passa |

NAT-27 é o caso que importa: é exatamente o jeito de "satisfazer o gate" sem
proteger nada. NAT-28 existe porque este projeto já produziu três falsos
positivos por scanner ingênuo (P3-R1 `randomUUID`, P4.0 `getNativeApiUrl` e
`Authorization`) — e a prosa deste repositório cita `https://` em vários
comentários.

Comportamento em runtime, em `tests/smoke/sessaoNativa.test.js`:

| Prova | O que verifica |
|---|---|
| P4T-01c | host puro vira `https://` |
| P4T-01d | host puro com porta vira `https://` |
| P4T-01e | `http://localhost:3333` é preservado |
| P4T-01f | cinco formas inaceitáveis devolvem `null` e `isNativeApiConfigured() === false` |
| P4T-01g | com base recusada, o login lança `PROVIDER_UNAVAILABLE` e **`fetch` não é chamado** |
| P4T-01h | host puro produz `https://backend.exemplo.invalido/auth/login` no `fetch`, não same-origin |

P4T-01g é a prova que fecha o item 3 deste relatório: o ponto não é recusar, é
**não mandar a senha para lugar nenhum**.

## 8. O que esta missão **não** fez

- **não** mudou `nativeRequest`. A concatenação literal continua, e continua
  correta — o contrato agora é que a base chega absoluta;
- **não** introduziu override de URL por query string ou storage. A porta que a
  P4.0 fechou segue fechada;
- **não** valida se o host existe ou responde. Isso é resposta de rede, não de
  configuração;
- **não** tocou no backend, no schema, nas migrations nem na P4.1.

## 9. Ação fora do código

A variável na Vercel deve ser corrigida para
`https://maike-production.up.railway.app`. Com esta missão o valor atual passa a
funcionar (host puro é normalizado), mas o valor explícito é o correto e o que o
`.env.example` documenta.

Duas pendências de segurança, ambas anteriores a esta missão e **ainda abertas**:

1. a senha do banco vazou em texto na resposta de uma ferramenta de automação e
   **não foi rotacionada**;
2. a senha do usuário de aplicação trafegou para a origem do frontend durante o
   período do defeito e deve ser trocada.

Nenhuma das duas é resolvida por código, e por isso nenhuma entra nesta PR.
