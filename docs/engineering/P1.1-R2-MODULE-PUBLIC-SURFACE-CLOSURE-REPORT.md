## 1. A causa comum dos três bloqueios

A R1 fechou o acesso **direto**: quem importasse `_providers`, o SDK ou o client
legado reprovava. O que ficou aberto foi o acesso **indireto** — e em cada caso
por um motivo diferente:

| # | Bloqueio | O que a R1 autorizou | O que faltou dizer |
|---|---|---|---|
| B1 | provider transitivo | `src/apis/<modulo>/**` pode importar `_providers` | pode **usar**, não **republicar** |
| B2 | página pula o service | UI não toca `_providers` | UI também não toca a API de dados |
| B3 | mensagem arbitrária | só `ApiError` tem mensagem exibível | e ela vem só do catálogo |

Os três têm a mesma forma: uma autorização necessária, escrita larga demais.
A R1 não errou ao autorizar — errou ao não delimitar.

## 2. R2-B1 — o provider vazando pela superfície pública

### O exemplo mínimo que passava

```js
// src/apis/empresa/index.js
export { empresaProvider } from '../_providers/base44Provider.js';
```

E então, numa página:

```js
import { empresaProvider } from '@/apis/empresa';
empresaProvider.create(dados);
```

O gate ficava verde, e cada verificação individual tinha razão de ficar:

- a página não importa `_providers` — importa `@/apis/empresa`;
- a página não importa `base44Client`;
- a página não contém `base44.entities`;
- `index.js` está em `src/apis/<modulo>/`, que a R1 autoriza;
- `providerLeaks` procurava o binding `base44`, não `empresaProvider`.

Cinco respostas certas somando uma conclusão errada. A fronteira voltava ao
ponto de partida — com o agravante de agora parecer arquitetada.

### A propriedade

Nenhum símbolo originado de `src/apis/_providers/**` pode ser exportado por
`src/apis/<modulo>/**`. O provider é dependência de implementação, nunca
superfície.

### A distinção que o analisador precisa fazer

```js
export const listEmpresas = () => empresaProvider.list(ordem);  // resultado → passa
export const getProvider  = () => empresaProvider;              // referência → reprova
```

Chamar um método devolve **o valor da chamada**. Devolver o identificador
devolve **o provider**, e a partir daí o consumidor faz o que quiser com ele.

`entregaProvider()` decide isso pela forma da expressão exportada: identificador
ligado ao provider, literal de objeto ou array que o contenha, função cujo corpo
conciso é o identificador, ou bloco com `return <identificador>`. Uma
`CallExpression` nunca entrega — é por isso que `empresaApi.js` continua válido.

Código novo: `P11-API-BOUNDARY-PUBLIC-PROVIDER-LEAK`.

## 3. R2-B2 — a página pulando o service

### O exemplo mínimo que passava

```js
// src/pages/Empresa.jsx
import { createEmpresa } from '@/apis/empresa';
```

Não toca `_providers`, não toca `base44` — e contorna `empresaService`, onde
mora a regra de nome duplicado. A validação que a P1.1 tinha acabado de mover
para o service ficava opcional.

### As camadas

| Camada | Pode importar |
|---|---|
| `src/pages/`, `src/components/`, `src/hooks/`, `src/Layout.jsx` | `src/services/` e `src/apis/_core/` — nunca API de dados |
| `src/services/` | `@/apis/<modulo>`, nunca arquivo interno, nunca `_providers/` |
| `src/apis/<modulo>/` | irmãos do próprio módulo e `_providers/` |

`_core/` não é API de módulo: o prefixo `_` o mantém fora da regra. É por isso
que `Empresa.jsx` continua importando `getApiErrorMessage` sem reprovar — e essa
é a razão de a exceção não precisar ser escrita como exceção.

### Superfície pública versus implementação

`src/apis/<modulo>/index.js` é a superfície. `src/apis/<modulo>/<modulo>Api.js`
é implementação. Quem está fora do módulo importa só o index; quem está dentro
importa irmãos à vontade.

**Decisão única sobre extensão:** o especificador é resolvido sem extensão, então
`@/apis/empresa`, `@/apis/empresa/index` e `@/apis/empresa/index.js` são o mesmo
alvo público. Não existem dois padrões contraditórios — SC7 documenta isso como
caso que passa.

Códigos novos: `P11-API-BOUNDARY-SERVICE-BYPASS` (UI tocando API de dados) e
`P11-API-BOUNDARY-MODULE-INTERNAL-BYPASS` (qualquer um de fora tocando
implementação interna). Separados de propósito: são violações diferentes, com
correções diferentes.

### Escalabilidade

Nada no analisador cita `empresa`. `moduleOf()` e `moduleTargetedBy()` derivam o
módulo do caminho, então `src/apis/lote/`, `src/apis/mapa/` e `src/apis/setor/`
já nascem cobertos. Há teste provando isso com um módulo `lote` sintético.

## 4. R2-B3 — `ApiError` ainda aceitava mensagem arbitrária

### O falso contrato

A R1 afirmou: **só `ApiError` tem mensagem exibível**. Verdadeiro do lado do
consumo — e vazio do lado da produção, porque o construtor fazia:

```js
super(info.message || MENSAGENS[code] || …);
```

Logo:

```js
new ApiError(API_ERROR_CODES.OPERATION_FAILED, { message: erroCru.message });
```

colocava o texto do provider — com URL, query string ou cabeçalho dentro —
direto no toast, agora **carimbado como confiável** por ser `ApiError`. A R1
fechou a porta e deixou a janela aberta.

### O contrato final

A mensagem pública é determinada **exclusivamente pelo código**:

```
code catalogado    → mensagem do catálogo
code desconhecido  → mensagem padrão interna
```

`message` recebido em `info` é **ignorado**, não recusado. A escolha é
deliberada: lançar transformaria um vazamento de texto em quebra de fluxo de
erro em produção, e o objetivo é o contrário. O contexto do chamador continua
inteiro em `cause` (não enumerável) e `details`, que a UI nunca exibe.

Mensagem parametrizada, se houver necessidade real, entra como código próprio com
formatador público — nunca texto livre. Não criei nenhum código novo agora: não
há uso real, e código sem consumidor é o que QLT-P11-03 proíbe.

### Auditoria de consumidores

`rg "new ApiError" src tests scripts` — 12 ocorrências. **Nenhuma** passava
`message`. A remoção não exigiu migração de nenhum chamador, e nenhum teste
dependia de texto livre.

### `details` — limite de escopo

Os usos reais são `{ id }` (update, delete) e `{ campo }` (assertArgument).
Ambos seguros, ambos com teste (AE7). Não construí sanitizador genérico: não há
passagem de payload para corrigir, e redaction sem necessidade seria complexidade
sem consumidor.

## 5. Implementação AST

Tudo por `ts.createSourceFile`, sem grep.

| Fato por arquivo | Para quê |
|---|---|
| `providerBindings` | nomes locais ligados a símbolos de `_providers/` |
| `publicProviderLeaks` | exports que entregam algum desses nomes |
| `moduleApiImports` | imports que endereçam `src/apis/<modulo>`, com `publico: boolean` |

A detecção de vazamento roda em **segunda passada**, depois de coletados todos os
bindings. Motivo concreto: `export { p }` pode aparecer antes do `import` que
declara `p` no texto do arquivo — imports são içados. Uma passada só perderia
esse caso, e há teste que o cobre explicitamente.

Cobertura sintática: `import`/`export … from`, `export *`, `export default`,
export specifiers com alias, variáveis e funções exportadas, `import()` dinâmico
literal, alias `@/`, caminho relativo e extensão opcional.

Não construí análise interprocedural. O objetivo é fechar os bypasses literais e
diretos; um `const x = provider; export const y = x;` de dois saltos ainda passa,
e isso está registrado como risco R2 abaixo em vez de escondido.
