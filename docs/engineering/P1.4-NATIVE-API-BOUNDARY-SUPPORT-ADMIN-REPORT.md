# P1.4 — Native API Boundary — Suporte, Administração e fechamento da P1

## 1. O que esta slice fecha

A P1.4 é a última slice da P1. Ela migra os **23 caminhos restantes** do
inventário e, com isso, leva os seis eixos de `gate:api-boundary` a zero:

```
importsLegacyClient  23 → 0
entitiesRefs         20 → 0
authRefs              8 → 0
integrationsRefs      2 → 0
functionsRefs         3 → 0
dynamicEntityFiles    2 → 0
```

O baseline versionado passa a ter as **seis listas vazias**. Isso muda o que o
gate significa: até aqui ele media "quanto falta migrar"; a partir daqui ele
impede *qualquer* reintrodução — não existe mais caminho legado tolerado.

A Base44 continua como provider temporário. A remoção do SDK é da P7.

## 2. Os três monkey patches globais

O achado central desta slice não estava no inventário de telas. Estava em
`src/api/base44Client.js`:

```js
installTextNormalization(base44Client);
applyDeleteGuards(base44Client);
installOfflineEntitySync(base44Client);
```

Cada um varria `client.entities` e substituía métodos **in place**, por entidade.
O efeito era invisível no ponto de uso: `Produto.list()` devolvia dado formatado,
`Produto.delete()` consultava uma tabela de dependências e podia lançar, e
`Lote.create()` podia gravar numa fila IndexedDB em vez de na rede.

Os três eram, também, o maior consumidor de acesso dinâmico do repositório:
`client.entities[entityName]` com nome vindo de uma lista de strings — a mesma
porta que `gate:api-boundary` existe para fechar, só que escondida atrás de uma
indireção.

Os três viraram composição explícita. Ver **D-PROD-20**.

| Antes | Depois |
|---|---|
| `installTextNormalization(client)` | `createNormalizedEntityAdapter({entityName, endpoint})` |
| `installOfflineEntitySync(client)` | `createOfflineEntityAdapter({entityName, operations, enabled, storage})` |
| `applyDeleteGuards(client)` | `assertExclusaoPermitida({carregadores, …})` nos services |

`src/lib/entityDeleteGuards.js` e `src/lib/offlineEntitySync.js` foram
**excluídos**, sem shim. `src/api/base44Client.js` voltou a ter 28 linhas e uma
responsabilidade: ler a configuração, criar o cliente, exportá-lo.

## 5. Decisões que mudam comportamento

Três, e todas são correção de defeito — não migração:

**5.1 `AuthContext` não usa o fallback offline.** `sessionService.getCurrentUser`
engole a falha e devolve o último usuário conhecido, o que é certo para telas que
precisam funcionar sem rede. Para o `AuthContext` seria o oposto do desejado: um
token expirado levaria ao cache em vez da tela de login. Por isso existe
`verificarAutenticacao`, que devolve um **veredito**
(`{autenticado, usuario, precisaAutenticar}`) em vez de exceção — e o
`AuthContext` deixa de inspecionar `status` de erro de provider.

**5.2 Upload sem `file_url` é falha.** O legado gravava `undefined` no campo e o
registro ficava apontando para lugar nenhum, sem erro. Agora
`arquivoService.enviarArquivo` lança `API_OPERATION_FAILED`.

**5.3 `calcularConsumoLotesPonderadoPorTempo` não estoura sem data.** O legado
fazia `parseDateLocal(evento.data_lancamento).getTime()` e explodia com
`null.getTime()` no meio do fechamento de período. Agora devolve lista vazia, e o
chamador cai no rateio simples por cabeças — que já era o fallback previsto para
lote sem alocação.

Além disso, **DBT-25** foi fechado e isso muda o dado gravado: `'12,5'` agora
grava 12,5 em vez de 12. O teste S3b, que fixava o truncamento, foi invertido.

## 6. Resultado parcial explícito

Cinco operações compostas passaram a declarar o que conseguiram fazer, em vez de
esconder a falha:

| Operação | Antes | Agora |
|---|---|---|
| exclusão de grupos/tipos de tarefa | `try { … } catch {}` vazio no laço | `{excluidos, bloqueados}` com código por item |
| exclusão de marcas/unidades/locais | `throw` no primeiro erro, sem dizer o que saiu | `{excluidas, falhas}` / `{excluidos, bloqueados}` |
| rename de local de estoque | tela dizia "Local atualizado!" com estado misto | `LOCAL_ESTOQUE_PARTIAL_OPERATION` com `details.etapas` |
| baixa e transferência de suplementação | `Error` cru propagado | `SUPLEMENTACAO_PARTIAL_OPERATION` com `details.etapas` |
| replay da fila offline | `continue` silencioso em entidade desconhecida | `OFFLINE_ENTITY_UNSUPPORTED`, item **preservado** na fila |

A última merece destaque: no antecessor, uma entrada de fila cuja entidade não
estivesse na lista de patch ficava presa para sempre, invisível, sem sinal
nenhum. Agora falha alto e não é descartada.

## 7. Códigos de erro novos

Doze, todos com consumidor e teste reais: `PRODUTO_NAME_CONFLICT`,
`PRODUTO_DELETE_BLOCKED`, `PRODUTO_PARTIAL_IMPORT`, `MARCA_NAME_CONFLICT`,
`UNIDADE_MEDIDA_DELETE_BLOCKED`, `LOCAL_ESTOQUE_DELETE_BLOCKED`,
`LOCAL_ESTOQUE_PARTIAL_OPERATION`, `GRUPO_ATIVIDADE_DELETE_BLOCKED`,
`TIPO_TAREFA_DELETE_BLOCKED`, `PERMISSAO_SELF_DELETE_BLOCKED`,
`SUPLEMENTACAO_PARTIAL_OPERATION`, `OFFLINE_ENTITY_UNSUPPORTED`.

Sumiu o pior padrão herdado: `throw new Error('DELETE_BLOCKED')` reconhecido pela

a frase usa vem de `details.quantidade`.

## 8. Gates: DBT-10, DBT-17, DBT-18

**DBT-10 — lint.** `eslint.config.js` passou a cobrir `src/**`, `scripts/**` e
`tests/**` inteiros, com globais por ambiente. A ampliação encontrou um defeito
real de imediato: `join` importado e não usado em `scripts/gates/lib/type-config.mjs`.

**DBT-17 — no-secrets.** A varredura passou a incluir arquivos não rastreados e
não ignorados. Três testes novos fixam o contrato: não rastreado com segredo
reprova, não rastreado seguro passa, ignorado não é varrido. O teste antigo, que
fixava o comportamento oposto, foi reescrito com a justificativa.

**DBT-18 — proveniência entre arquivos.** O gate passou a reprovar o provider
passado como **argumento**. A regra reusa `ehCapacidade`, a mesma classificação
dos exports, e tem controle positivo: passar o **resultado** de uma chamada
continua permitido. Receptor de `.call`/`.apply`/`.bind` é excluído — é execução,
não repasse.

Essa regra encontrou um vazamento real na própria P1.4:
`Object.freeze({ ...sessionProvider.capacidades })` entregava uma referência para
dentro do provider. Virou `sessionProvider.capacidades()`, que devolve dado.

### Sobre a redução de 405 diagnósticos de tipo

Não veio de migração. Veio de uma anotação `@type {any}` em
`src/components/ui/button.jsx`. `React.forwardRef` com parâmetro implicitamente
`any` fazia o TypeScript inferir um componente que, segundo o verificador, não
aceita **nenhuma** prop — então cada `<Button variant=… size=…>Texto</Button>` do
produto virava um `TS2322`. Eram centenas, e nenhum indicava defeito. Zero efeito
em runtime: o componente é o mesmo, byte por byte.

Foi feito nesta slice porque era necessário: a mudança de tipo do retorno de uma
query em `Produtos.jsx` alterava o **texto** de um diagnóstico existente, e a
catraca trata texto novo como fingerprint novo. Reproduzir o texto antigo exigiria
o tipo que o SDK produzia — impossível depois que a normalização passa pelo
adapter. Eliminar o diagnóstico foi a saída correta; manter o ruído seria a
errada.

## 12. Riscos que permanecem

Nenhum destes foi resolvido, e nenhum é declarado resolvido:

- **Base44 como provider temporário.** A remoção é da P7;
- **`max + 1` sem concorrência segura.** A regra saiu das telas para os services,
  o que a torna testável — mas duas criações simultâneas ainda podem receber o
  mesmo número. Só sequência no servidor resolve (P3);
- **Operações compostas sem ACID.** A P1.4 tornou a falha parcial *visível*, não
  atômica (DBT-19);
- **Não há backend nativo neste repositório** (DBT-23);
- **Bundle único de ~2,50 MB**, sem code splitting (DBT-06);
- **`npm audit`** reporta vulnerabilidades transitivas (DBT-11);
- **OWNER-SECURITY-01 continua aberto**: revogar e rotacionar a chave do Google
  Maps, restringir por HTTP referrer, restringir às APIs realmente usadas (Maps
  JavaScript API e Geometry) e monitorar. A chave antiga permanece no histórico
  Git.

## 13. Escopo negativo

Não foram tocados: rotas, menu, permissões funcionais, design visual, schemas
Base44, `base44/functions`, plugin do Vite, `requiresAuth`, loader do Google
Maps, versões de pacote, Node ou TypeScript. Nenhum login novo, backend fake,
repository genérico, adapter por nome, domínio novo, tela nova ou menu novo.

**P2 e P3 continuam não iniciadas.**

## 14. Estado da P1

A P1 está **tecnicamente fechada nesta branch**: os seis eixos em zero, o
baseline com as seis listas vazias, o registry igual ao manifesto e a única porta
para a Base44 sendo `src/api/base44Client.js`, consumido apenas por
`src/apis/_providers/base44Provider.js`.
