# P4.0-R4 — Login nativo: same-origin ampliado + bypass emergencial

**Data:** 2026-10-23  
**Decisão:** D-PROD-37  
**Branch:** `cursor/auth-skip-login-fix-api-516d`

## Problema

Após o merge de D-PROD-36, usuários ainda viam **“Serviço de dados indisponível”**
ou falha no login quando:

1. O bundle tinha `VITE_MAIKE_API_URL` fixo em um host e a página abria em outro
   HTTPS (preview, alias, domínio customizado).
2. Um token antigo em `sessionStorage` impedia revalidação e a UI não oferecia
   caminho claro para entrar de novo com usuário e senha.

O formulário de login **já não pede cliente** (D-PROD-33); o tenant vem do
servidor após autenticação.

## Mudanças

| Área | Alteração |
|------|-----------|
| `getNativeApiUrl()` | Se origem HTTPS ≠ env e não for split local, usa `window.location.origin` |
| `VITE_SKIP_NATIVE_LOGIN` | Build flag: sessão fake, pula restore |
| `NativeSessionUnavailable` | Botão “Entrar com usuário e senha” limpa token e abre login |
| `AuthContext` | `encerrarValidacaoEIrParaLogin()` |

## Operação (Vercel)

Para **desativar login na UI** até novo fix:

1. Project → Settings → Environment Variables  
2. `VITE_SKIP_NATIVE_LOGIN` = `true` (Production e Preview)  
3. Redeploy (variável `VITE_` só entra no bundle no build)

Para **reativar login**: remover a variável e redeployar.

Credenciais quando login estiver ativo: usuário `admin` (sem campo cliente na UI).

## Limitações do bypass

- O app monta com usuário sintético; chamadas nativas autenticadas **podem falhar**
  sem JWT válido.
- Não altera RLS/tenancy no backend; `Cliente` permanece no schema (D-PROD-22).
