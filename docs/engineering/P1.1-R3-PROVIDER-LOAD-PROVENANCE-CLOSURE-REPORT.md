## 1. A causa técnica

A R2 declarou a propriedade em termos absolutos:

> Nenhum símbolo originado de `src/apis/_providers/**` pode ser exportado por
> `src/apis/<modulo>/**`, em nenhuma forma.

O analisador não sustentava esse "em nenhuma forma". Duas lacunas concretas:

**1. Origem reconhecida, proveniência perdida.** `registrarEspecificador()` já
reconhecia `import()`, `require()` e `import x = require()` — mas só para marcar
`importsProviders`. O conjunto `providerBindings`, que alimentava a detecção de
vazamento, era preenchido **exclusivamente** por `ImportDeclaration` estático. A
informação chegava ao gate e morria antes do analisador de expressão.

**2. Só identificador contava como entrega.** `entregaProvider()` reconhecia o
identificador ligado ao provider. Não reconhecia acesso a **membro** — nem
`providers.empresaProvider` (namespace), nem `empresaProvider.create` (método).

O resultado é que a R2 fechou a porta que testou e deixou abertas as que
descreveu. A CI verde da R2 era real; ela não provava estas formas.

## 2. R3-B1 — import dinâmico exportado

```js
// src/apis/empresa/index.js
export const getProviderModule = () => import('../_providers/base44Provider.js');
```

O consumidor recebe o namespace inteiro:

```js
const m = await getProviderModule();
m.empresaProvider.create(dados);
```

Nenhuma análise interprocedural é necessária para ver isso — o vazamento está na
própria expressão exportada. Três formas cobertas: `() => import(…)`,
`async () => (await import(…)).empresaProvider` e `export default import(…)`.

Um detalhe de implementação que quase virou bug meu: a passada de detecção
estava condicionada a existir pelo menos um binding do provider. Estes casos não
ligam nome local nenhum — a origem é inline. A passada roda **sempre**.

## 3. R3-B2 — require e desestruturação

```js
export const getProvider = () => require('../_providers/base44Provider.js').empresaProvider;
const providers = require('../_providers/base44Provider.js');   export { providers };
const { empresaProvider } = require('../_providers/base44Provider.js');  export { empresaProvider };
```

As três reprovam. A justificativa "CommonJS não é usado hoje" não se aplica:
a R1 declarou `require()` coberto, e sintaxe declarada coberta precisa de prova
ponta a ponta. Declarar cobertura sem prova é pior do que não cobrir — cria
confiança que o gate não sustenta.

## 4. R3-B3 — namespace import e acesso a membro

```js
import * as providers from '../_providers/base44Provider.js';
export const getProvider = () => providers.empresaProvider;   // reprova
export const bag = { empresa: providers.empresaProvider };    // reprova
export default providers.empresaProvider;                     // reprova
```

O binding de origem é o namespace; a expressão exportada entrega um membro dele.

## 5. R3-B4 — referência de método do provider

```js
export const createRaw = empresaProvider.create;                       // reprova
export const rawOperations = { create: empresaProvider.create };       // reprova
export const getCreate = () => empresaProvider.create;                 // reprova
export const createEmpresa = (dados) => empresaProvider.create(dados); // passa
```

A referência crua do método é vazamento porque permite chamar a operação fora de
`runProviderCall`, da normalização de erro, do contrato da API de módulo e da
validação de argumento. Entregar `create` é entregar a capacidade; entregar
`create(dados)` é entregar o dado.

## 6. R3-B5 — parser por extensão, e uma correção do meu próprio diagnóstico

`ts.createSourceFile` era chamado com `ts.ScriptKind.JS` fixo. Implementei
`scriptKindOf()` mapeando `.js`/`.mjs`/`.cjs` → JS, `.jsx` → JSX,
`.ts`/`.mts`/`.cts` → TS, `.tsx` → TSX.

**Mas o diagnóstico da missão sobre este ponto não se confirmou, e registro
isso em vez de deixar passar.** Medi o comportamento real do parser:

```
ScriptKind.JS  → ImportEqualsDeclaration presente: true
ScriptKind.TS  → ImportEqualsDeclaration presente: true
```

O parser do TypeScript é tolerante: produz o nó `ImportEqualsDeclaration` mesmo
sob `ScriptKind.JS`. Portanto **o que faltava para PD10/PD11 não era o
`ScriptKind`** — era registrar o binding desse nó, que a R2 simplesmente não
fazia. Escrevi um teste que assumia o contrário; ele falhou, e a correção foi no
teste, não no código. Fica registrado porque a suíte pegou um erro meu.

O mapeamento por extensão continua correto e necessário — só não pelo motivo
alegado. Onde ele importa de verdade, medido:

```
JSX sob ScriptKind.TS  → 4 erros de parse
JSX sob ScriptKind.TSX → 0 erros de parse
```

Um `.tsx` lido como TS não é analisado; arquivo que o parser não entende é
arquivo cujas invariantes não são verificadas. Há teste para exatamente isso.

## 7. O modelo de proveniência implementado

Três conceitos, em vez de uma lista de nomes.

**Origem de proveniência** — um nome local ou uma expressão que produz algo
derivado de `_providers/`:

| Forma | Exemplo |
|---|---|
| import estático nomeado / default / namespace | `import * as p from '…/_providers/…'` |
| `import x = require(…)` | `import p = require('…/_providers/…')` |
| `import()` literal do módulo provider | `import('…/_providers/…')` |
| `require()` literal do módulo provider | `require('…/_providers/…')` |
| desestruturação de qualquer origem | `const { empresaProvider } = require(…)` |
| alias local de qualquer origem | `const raw = empresaProvider` |

**Expressão de origem** — `origemProvider()` responde "isto avalia para uma
capacidade do provider?":

- identificador ligado a uma origem;
- `PropertyAccess`/`ElementAccess` enraizado numa origem;
- `await` de uma origem;
- `import('<provider>')` e `require('<provider>')` — que são **origem**, não
  resultado, porque o valor que produzem é o namespace do provider;
- **qualquer outra `CallExpression` → falso**, porque devolve o resultado da
  operação, e resultado é dado.

Essa última linha é a regra inteira em uma frase.

**Entrega** — `entregaProvider()` embrulha o anterior: origem direta, ou objeto,
array, spread, função de corpo conciso ou bloco com `return` que devolva origem.

### Ponto fixo para alias local

Alias podem encadear e podem ser declarados depois do uso. A coleta de origens
roda em laço até estabilizar (limite de 8 voltas, com saída antecipada). Termina
porque cada volta só **adiciona** nomes e o conjunto de nomes do arquivo é
finito. É isso que fecha PD16 — o alias local **não** foi empurrado para DBT-18.

### Ordem das passadas

1. imports e especificadores (origens diretas);
2. ponto fixo de aliases locais;
3. detecção de vazamento nos exports.

A terceira é separada porque `export { p }` pode aparecer antes do `import` que
declara `p` — imports são içados — e porque só depois do ponto fixo o conjunto
de origens está completo.

### A invariante escolhida para PD13/PD14

**Permitir.** Única, aplicada aos dois, e coerente com a regra geral: a expressão
exportada devolve o **resultado da chamada**, não a capacidade. Proibir
`import()`/`require()` dentro da API de módulo seria uma segunda regra, com uma
justificativa diferente (preferência por import estático), e não é o que esta
missão precisa provar. A preferência arquitetural por imports estáticos continua
válida como preferência — não virou invariante silenciosa.
