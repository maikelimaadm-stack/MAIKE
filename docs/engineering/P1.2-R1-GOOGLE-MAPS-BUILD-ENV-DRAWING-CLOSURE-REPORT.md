## 4. Por que `tail` não pode ser gate

`npm run verify:all 2>&1 | tail -6` só imprime quando o processo **inteiro**
termina: `tail` precisa ver o fim do fluxo para saber quais são as últimas seis
linhas. Durante os ~100 s de execução a saída fica em branco, e a interface
aparenta travamento. Pior: as 6 linhas finais são o rodapé do resumo, então uma
etapa vermelha no meio pode não aparecer.

Substituído por `tee` num arquivo, com leitura seletiva depois — o progresso
continua visível e nada é descartado.

## 5. Por que faltava `pipefail`

Em `a | b`, o status do pipeline é o status de `b`. `npm run verify:all | tail`
devolve o status do `tail`, que é 0 mesmo quando o `verify:all` falha. Somando
os outros dois defeitos:

- `;` antes do `git push` torna o push **incondicional** — ele roda mesmo com a
  verificação vermelha;
- o laço `for i in 1 2 3 4` com `sleep` esconde o erro real e prolonga a espera.

Juntos, os três significam: **um `verify:all` vermelho podia ser seguido de
push.** Não foi o que ocorreu nesta branch — o verify saiu verde e a CI
confirmou —, mas a possibilidade existia e não é aceitável.

Forma adotada nesta missão:

```
set -o pipefail
npm run verify:all 2>&1 | tee /tmp/p12-r1-verify.log
status=${PIPESTATUS[0]}
test "$status" -eq 0
```

Push apenas depois de exit 0 confirmado, uma tentativa, erro visível.

## 6. Causa de build do Vite — o que foi medido

O R1-B1 afirma que `import.meta.env?.[nome]` não é materializado no build e por
isso a variável chega `undefined` ao bundle. **Medi, e não é o que acontece.**

Prova isolada, projeto Vite mínimo, build de produção real:

```js
const dinamico = (nome) => import.meta.env?.[nome];
window.__A = dinamico('VITE_PROBE_ALPHA');
window.__B = import.meta.env.VITE_PROBE_BETA;
```

Bundle emitido:

```js
const s={BASE_URL:"/",DEV:!1,MODE:"production",PROD:!0,SSR:!1,
         VITE_PROBE_ALPHA:"ALPHA_MARKER_X",VITE_PROBE_BETA:"BETA_MARKER_Y"}
…
window.__A=u("VITE_PROBE_ALPHA");window.__B="BETA_MARKER_Y"
```

Quando o Vite encontra um `import.meta.env` que não consegue especializar, ele
**materializa o objeto inteiro** como literal e reescreve o acesso para
indexá-lo. A leitura dinâmica funciona. O mesmo foi confirmado no repositório
real: com a forma antiga restaurada temporariamente, o marcador sintético
apareceu no bundle.

**O que a forma dinâmica realmente causa** — e este é o motivo da troca:

| Forma | O que entra no bundle do cliente |
|---|---|
| dinâmica | o objeto env **inteiro**, incluindo `VITE_*` que o código nunca referencia |
| estática | apenas o valor referenciado, inline |

Medido com uma variável nunca usada pelo código (`VITE_PROBE_NUNCA_USADA`): a
forma dinâmica a despejou no bundle; a estática, não. Ou seja, a forma antiga
transformava **qualquer** `VITE_*` futura em conteúdo público do bundle, mesmo
sem uso. É contenção de superfície, não correção de leitura — e é uma melhoria
real, só não é a que a missão descreve.

**Então qual é a causa do sintoma em produção?** A mensagem observada é
`MAPS_CONFIG_MISSING`, emitida quando a chave está ausente **no bundle**. Como a
leitura funcionava, a explicação compatível com a evidência é que
`VITE_GOOGLE_MAPS_API_KEY` não estava presente **no momento do build**, no
serviço que executa `npm run build`. Isso é exatamente o que a seção 24
descreve como ação ainda pendente do proprietário. Não afirmo qual das
possibilidades ocorreu — não tenho acesso à plataforma e não vou inventar
confirmação.

Há ainda um segundo caminho para o mapa falhar, independente da chave, e esse
está provado: o R1-B2.

## 7. Código antes/depois

Sem valores, sem chave.

**Antes** — um leitor genérico por nome:

```js
const readEnv = (nome) => {
  try {
    const valor = import.meta.env?.[nome];
    return typeof valor === 'string' && valor.trim() ? valor.trim() : null;
  } catch { return null; }
};
```

**Depois** — uma função por variável, com a propriedade escrita literalmente:

```js
const normalizarEnv = (valor) =>
  typeof valor === 'string' && valor.trim() ? valor.trim() : null;

const lerGoogleMapsApiKey  = () => { try { return normalizarEnv(import.meta.env.VITE_GOOGLE_MAPS_API_KEY); } catch { return null; } };
const lerBase44AppId       = () => { try { return normalizarEnv(import.meta.env.VITE_BASE44_APP_ID);       } catch { return null; } };
const lerBase44BackendUrl  = () => { try { return normalizarEnv(import.meta.env.VITE_BASE44_BACKEND_URL);  } catch { return null; } };
```

A chave continua lida **a cada chamada**, não congelada na carga do módulo: os
testes trocam o ambiente depois de importar. Isso não conflita com a
substituição do Vite — o literal já está no corpo da função quando o bundle é
gerado.

O comentário do módulo descreve o mecanismo **medido**, não o suposto. Registrar
no código uma explicação que a medição contradiz seria plantar uma causa falsa
para a próxima pessoa.

## 12. Contrato final do loader


4 testes que dependiam do método ausente.

**Correção:** troca por `readdirSync('src', { recursive: true })`, disponível
desde o Node 18.17 e portanto válido nas duas versões. A revalidação foi feita
com **Node 20.19.0 instalado localmente** — `nvm install 20.19.0` — em vez de
confiar de novo no Node da máquina.

**Lição registrada:** verificação local que roda numa versão de runtime
diferente da CI não é verificação. O `.nvmrc` existe justamente para isso e eu
não o respeitei antes do primeiro push. Não é caso para gate novo — é para usar
a versão do `.nvmrc` antes de empurrar.
