## 2. O default de `tipo`

### O que estava errado

`base44/entities/Setor.jsonc`:

```json
"tipo": {
  "type": "string",
  "enum": ["Próprio", "Arrendado", "Parceria", "Terceiros"],
  "default": "Próprio"
}
```

A P4.1 trouxe o enum (no schema HTTP) e a obrigatoriedade (`NOT NULL`), e deixou
o **default** para trás:

```prisma
tipo               String   @db.VarChar(32)        // sem @default
```

```sql
"tipo" VARCHAR(32) NOT NULL,                        -- sem DEFAULT
```

Divergência objetiva, e do tipo que não quebra nada em teste: enquanto todo
caminho de escrita informar `tipo`, ninguém percebe. O default existe justamente
para o caminho que ninguém previu.

### Por que a correção é aditiva

A migration `20260909112833_p4_1_setor_native` está mergeada **e aplicada no
ambiente real**, com o checksum registrado em `_prisma_migrations`. Editá-la
para "sempre ter tido" o default mudaria esse checksum e quebraria todo
`migrate deploy` seguinte com *migration was modified after it was applied*.

A cadeia passa a ter dois passos:

| Passo | Efeito |
|---|---|
| `20260909112833_p4_1_setor_native` | cria `"tipo" VARCHAR(32) NOT NULL`, sem default |
| `20260909201703_p4_1_r2_setor_tipo_default` | `ALTER COLUMN "tipo" SET DEFAULT 'Próprio'` |

**A migration histórica não foi tocada.** Reescrever histórico para que ele
pareça correto desde sempre é a forma mais limpa de perder a capacidade de
confiar no histórico.

### SQL efetivo

```sql
ALTER TABLE "Setor" ALTER COLUMN "tipo" SET DEFAULT 'Próprio';
```

### Prova contra PostgreSQL real

```
$ npx prisma migrate deploy
  └─ 20260908174141_p3_foundation/
  └─ 20260909112833_p4_1_setor_native/
  └─ 20260909201703_p4_1_r2_setor_tipo_default/
All migrations have been successfully applied.

$ information_schema.columns → Setor.tipo
tipo | NO | 'Próprio'::character varying
```

Contra PostgreSQL 16 **descartável**, criado e destruído na sessão. Nenhum banco
de produção, staging, Supabase externo ou do proprietário.

## 3. A API continua exigindo `tipo`

O default **não** torna o campo opcional. `POST /setores` continua exigindo
`empresa_id`, `nome` e `tipo`; sem `tipo` a resposta é 400
`REQUEST_VALIDATION_FAILED` e nada é gravado.

O default é **última barreira de persistência** — garantia de que nenhum caminho
de escrita, hoje ou depois, grave a coluna vazia. Não é permissão para o cliente
omitir a intenção do usuário. Afrouxar o schema HTTP porque o banco tem default
trocaria uma escolha explícita por um palpite silencioso, e o palpite ficaria
gravado como se fosse decisão de quem cadastrou.

## 4. Provas

Nenhum gate estático prova default **físico**: ler `SET DEFAULT` no arquivo prova
que o texto está lá, não que o PostgreSQL aplicou.

| Prova | O que estabelece |
|---|---|
| `P41R2-BE-01` | `information_schema.columns` traz `column_default` com `'Próprio'` e `is_nullable = NO` |
| `P41R2-BE-02` | `INSERT` **cru** omitindo a coluna → linha persistida com `tipo = 'Próprio'` |
| `P41R2-BE-03` | `POST /setores` sem `tipo` → 400, zero `Setor`, zero `AuditLog`, **zero sequência consumida** |
| `P41R2-BE-04` | controle positivo: `tipo: 'Arrendado'` continua sendo respeitado |

`P41R2-BE-02` usa `INSERT` cru de propósito: `prisma.setor.create` poderia
preencher o valor do lado do cliente, e o teste passaria com a coluna sem default
nenhum — provaria o Prisma, não a migration.

`P41R2-BE-04` existe porque um default aplicado no lugar errado — sobrescrevendo
o valor enviado — passaria despercebido sem ele.

### Gate

`P41-SETOR-TIPO-DEFAULT`, absoluto, dentro de `gate:setor-native` (nenhuma
cerimônia nova: `verify:all` continua com 20 etapas).

A regra julga o **estado final da cadeia**, em ordem cronológica, e não arquivo
isolado — porque a migration da P4.1 legitimamente não tem o default:

| Cadeia | Veredito |
|---|---|
| `CREATE TABLE` sem default → `SET DEFAULT 'Próprio'` | passa (histórico real) |
| `CREATE TABLE` sem default, nada depois | reprova |
| `SET DEFAULT 'Arrendado'` | reprova |
| `SET DEFAULT 'Próprio'` → `DROP DEFAULT` | reprova (a ordem é respeitada) |

| Prova | Mutilação | Esperado |
|---|---|---|
| `SN-19` / `P41R2-G-01` | schema perde `@default("Próprio")` | reprova |
| `SN-20` / `P41R2-G-02` | some a migration corretiva (estado real da main pós-#14) | reprova |
| `SN-21` / `P41R2-G-03` | default vira `'Arrendado'` | reprova |
| `SN-21b` | `DROP DEFAULT` depois de um `SET` | reprova |
| `SN-22` / `P41R2-G-04` | **controle positivo:** schema e migration só com prosa citando `@default("Próprio")` e `SET DEFAULT 'Próprio'` | reprova — prosa não declara nada |
| `SN-22b` | controle positivo: a fixture correta não emite o código | passa |

`SN-22` é o caso que separa regra de teatro: comentário de SQL é removido antes
da varredura, e comentário de linha é removido dos atributos do campo antes de
checar o `@default`.

## 5. Correção factual — `syncEntityReferences`

O SSOT afirmava que a propagação de Setor alcança "quatro entidades", repetindo a
lista da guarda de exclusão. O código diz outra coisa.

`base44/functions/syncEntityReferences/entry.ts` tem **15 regras** no bloco
`Setor`, sobre **seis destinos distintos**:

| # | Destino | Na guarda de exclusão? |
|---|---|---|
| 1 | `AreaPastagem` | sim |
| 2 | `PontoSuplementacao` | **não** |
| 3 | `Lote` | **não** |
| 4 | `LancamentoTarefa` | sim |
| 5 | `MovimentacaoMapa` | sim |
| 6 | `MovimentacaoPecuaria` | sim |

`deleteRules.Setor` lista **quatro**.

**São contratos diferentes**, e o SSOT os tratava como o mesmo. Um responde
"quem exibe o nome do setor e precisa ser atualizado quando ele muda"; o outro
responde "quem impede o setor de ser apagado". Um destino pode estar em um e não
no outro sem que isso seja bug: `Lote` guarda o nome do setor para exibição sem
que isso, por si, bloqueie a exclusão.

### O que **não** foi feito

Esta R2 **não** acrescenta dependências ao `deleteGuardService`. O `DELETE` de
Setor continua fechado (D-PROD-25 §D), então mexer na guarda agora mudaria
comportamento sem consumidor e sem prova de necessidade.

### Critério de reabertura registrado

> `DELETE /setores/:id` **não** pode ser reaberto com a frase "as quatro
> dependências migraram". Antes de reabrir, a fatia responsável precisa
> reconciliar explicitamente: `deleteRules`; as FKs nativas realmente criadas;
> os **seis** destinos de `syncEntityReferences`; a semântica de `Lote`; e a
> semântica de `PontoSuplementacao`.

Registrado como DBT-30.

## 6. Sem backfill (D-PROD-27)

Decisão do **proprietário**: os registros históricos da Base44 não serão
migrados. As capacidades nativas nascem vazias e o necessário é recadastrado.

Some do caminho: backfill, dual-write, reconciliação de contagem/checksum,
rollback de dado e downtime de corte. Sobra migração de **capacidade**.

### O que a decisão não autoriza

Está escrito porque "não vamos migrar dado" é fácil de ler como "podemos apagar
dado":

- **não** apagar `Cliente`, `Usuario`, `AuditLog`, `EntidadeCodigoSequencia`,
  `RegistroAnexo` ou `Setor` já existentes no backend nativo;
- **não** apagar nada da Base44 — ela é a fonte de 37 entidades em produção;
- **não** fazer limpeza automática em lugar nenhum sem ação explícita e nomeada
  do proprietário.

Cada capacidade migrada aparece zerada na tela até ser recadastrada. É esperado,
e não deve ser "corrigido" com carga improvisada.

A premissa fica oficializada. O replanejamento do ROADMAP é trabalho da próxima
fatia, com auditoria própria — **nenhum model novo entrou nesta R2**.

## 7. DEPLOY-MIGRATION-01

Risco operacional registrado, não resolvido nesta fatia.

O `preDeployCommand` do Railway está vazio desde que `prisma migrate deploy`
travou contra o pooler de transação (`:6543`). A migration de `Setor` foi
aplicada **manualmente** no ambiente real.

Consequência que precisa estar dita sem maquiagem:

> CI verde, Vercel verde e deploy do Railway concluído **não** significam que
> uma migration chegou ao banco de produção. São fatos diferentes. Enquanto o
> pipeline não aplicar migrations, a aplicação depende de ação operacional
> separada.

Isto vale para a migration desta R2: **ela não foi aplicada em produção por esta
fatia**, e nada aqui deve ser lido como se tivesse sido.

É bloqueador para a próxima onda de domínio: migrar várias capacidades sem um
caminho repetível e seguro de `migrate deploy` no deployment multiplica a chance
de o código chegar antes do schema.

Esta R2 **não** alterou configuração do Railway. Há um patch do proprietário em
*staged* naquele serviço, e mexer às cegas arriscaria commitá-lo ou descartá-lo.

mesmo cuidado que varrer com regex.

`README_AI.md` e D-PROD-25 §K.

estado corrente: `P4.1-SETOR-NATIVE-PERSISTENCE-REPORT.md`. Relatório de missão
descreve o que aquela missão entregou; reescrevê-lo para virar fotografia do
presente apagaria a procedência.

### 10.2 O build: não havia divergência entre ambientes

O relatório entregue ao proprietário informou **3.946 módulos** para este HEAD.
A CI do mesmo HEAD registrou **3.948**.

Reconciliado por medição direta, e a explicação é mais simples do que
"ambiente":

```
LOCAL (nesta execução, HEAD f359f2a)
  ✓ 3948 modules transformed
  dist/assets/index-DoKSZO6c.js   2,506.83 kB │ gzip: 672.11 kB

CI (run 34401370069, job 102633807571, mesmo HEAD)
  3948 modules transformed
  dist/assets/index-DoKSZO6c.js   2,506.83 kB │ gzip: 672.11 kB
```

**Local e CI concordam** — mesmo número de módulos, mesmo hash de bundle, mesmos
tamanhos. O `3.946` não veio de outro ambiente: veio de um número que **não foi
medido para este HEAD**. O comando usado na coleta terminava em `tail -3`, que
descartou justamente a linha `modules transformed`, e o valor escrito foi
herdado de contexto anterior.

Nenhum código foi alterado para fazer contagem coincidir, porque não havia nada
a fazer coincidir. O defeito era de procedência da evidência, não de build.
