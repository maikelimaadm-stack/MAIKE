**Data:** 2026-08-03 · **Branch:** `claude/p1-1-native-api-boundary-empresa` · **PR:** draft
**Origem:** `main` em `508cf62949530e8a55bd1b4c55a68dd1da2e6b64` (merge da PR #1)

Primeira slice da **P1 — Native Foundation Bootstrap**. A P1 continua em
andamento; esta PR entrega a fundação e um piloto.

---

## 1. O problema que esta slice ataca

Depois da P0.1 o produto ficou com 371 chamadas `base44.entities` **dentro de
componentes React** (DBT-01). Nessa forma, trocar de provider é impossível de
fatiar: qualquer substituição exigiria tocar em todas as telas ao mesmo tempo.

A saída não é um wrapper que renomeia a Base44 — isso mudaria o import e
manteria o acoplamento. É uma fronteira real, onde a página deixa de falar o
formato do provider:

```
Empresa.jsx  →  empresaService  →  empresaApi  →  base44Provider  →  base44Client
   UI            regra de           adaptador       adapter          SDK legado
                 negócio            de dados        temporário
```

O que a página sabe hoje: `empresaService.listEmpresas()`.
O que ela sabia antes: `base44.entities.Empresa.list('-created_date')`.

não registrei nenhuma das outras 37 entidades — elas entram quando tiverem
consumidor migrado (SCL-P11-02).

## 3. Runtime config

`src/lib/app-params.js` foi **removido**, sem shim. Os dois consumidores reais
(`src/api/base44Client.js` e `src/lib/AuthContext.jsx`) passaram a usar
`getDataProviderConfig()`, e `src/lib/googleMaps.js` passou a ler a chave por
`runtimeConfig` em vez de `import.meta.env` direto.

Comportamento preservado, item por item:

| Comportamento | Estado |
|---|---|
| precedência query string > `localStorage` > env | preservado |
| persistência com prefixo `base44_` | preservado |
| `access_token` removido da URL na primeira leitura | preservado |
| resolução única no carregamento do módulo | preservado |
| `requiresAuth: false` | **não tocado** |
| autenticação | **não tocada** |

Detalhe que importa: a resolução acontece **uma vez**, no import. Isso não é
detalhe de implementação — é o que garante que `access_token` só saia da URL na
primeira leitura. Resolver de novo depois devolveria `null` para quem chegou
pela query string.

Endurecimentos: `localStorage` que lança (modo privado, cota) não derruba mais a
aplicação, e `URLSearchParams` em erro não propaga.

**Segurança (QLT-P11-05).** A API devolve valores, nunca despeja o objeto.
`describeRuntimeConfig()` expõe apenas presença/ausência — há teste provando que
o serializado não contém token, chave nem app id, e outro provando que o módulo
não escreve nada em `console` ao resolver a configuração.

## 4. Padrão de erro

`ApiError` com `name`, `code`, `message`, `operation`, `resource`, `cause`,
`retryable` e `details`.

| Código | Uso |
|---|---|
| `API_OPERATION_FAILED` | falha genérica do provider |
| `API_INVALID_ARGUMENT` | argumento inválido, antes de chamar o provider |
| `API_PROVIDER_UNAVAILABLE` | rede/timeout/502/503/504 — único `retryable` |
| `EMPRESA_NAME_CONFLICT` | regra de negócio do módulo |

Quatro códigos, todos com uso real. O erro cru do provider — que pode carregar
`response`, `config` e afins — fica em `cause`, fora da mensagem pública e fora
de `JSON.stringify`. `getApiErrorMessage(erro, fallback)` nunca devolve
`undefined`.

A UI identifica conflito por **código**, não por texto.

## 5. Provider temporário

`src/apis/_providers/base44Provider.js` é o único arquivo de `src/apis/` que
importa `@/api/base44Client`. O objeto do provider **não é exportado** em nenhuma
forma. O registry é literal:

```js
const ENTITY_REGISTRY = Object.freeze({
  Empresa: base44.entities.Empresa,
});
```

`endpointOf()` é privado e lança para nome fora do registry — nome desconhecido
é erro de programação, não condição de runtime. O adapter expõe só `list`,
`create`, `update` e `delete`, preservando a ordenação `-created_date`. Nada de
paginação, cache ou filtro que o provider atual não ofereça.

---

## 6. Empresa API e service

A API valida argumento, encaminha ao provider e normaliza falha. Não importa
React, não conhece React Query, não mostra toast, não aceita `entityName`. `list`
sempre devolve array — se o provider devolver `undefined`, a fronteira entrega
`[]`, para a UI não ter que se defender disso.

O service carrega a regra de nome duplicado, com o comportamento observável
idêntico ao anterior: `trim`, sem diferença de caixa, `create` recusa nome
existente, `update` ignora o próprio registro, mesma mensagem.

**Uma diferença real, e ela é uma correção.** A validação antiga comparava contra
`empresas` — a lista que o React Query tinha em memória. A validação dependia do
estado do cache: com cache vazio ou desatualizado, um nome duplicado passava. O
service compara contra a leitura atual do provider.

## 8. `gate:api-boundary`

Entra no `verify:all` depois de `product-scope` e antes de `source-closure` —
**13 etapas**.

O baseline guarda **listas ordenadas de caminhos**, não contagem. Contagem
sozinha deixaria passar troca: remover um acesso aqui e criar outro ali fecharia
o número e abriria caminho novo. Por isso rename é regressão.

Eixos: `importsLegacyClient`, `entitiesRefs`, `authRefs`, `integrationsRefs`,
`functionsRefs`, `dynamicEntityFiles`.

O adapter autorizado fica **fora** das listas: ele não é dívida, é a fronteira.

### Uma decisão de escopo que precisa ficar registrada

A invariante "acesso dinâmico a entidade reprova" não podia valer para todo
`src/` nesta slice: três arquivos legados — `loteRepository.js`,
`entityDeleteGuards.js`, `offlineEntitySync.js` — já fazem
`base44.entities[nome]`, e migrá-los está explicitamente fora desta PR.

Aplicar a regra repo-wide deixaria o gate impossível de passar. Ignorar os três
seria frouxo. A solução: **absoluta dentro de `src/apis/`** (onde é desenho
errado, não dívida herdada) e **congelada por arquivo** fora dela, no eixo
`dynamicEntityFiles` — os três só podem sair, nenhum novo entra. Registrado como
DBT-16.
