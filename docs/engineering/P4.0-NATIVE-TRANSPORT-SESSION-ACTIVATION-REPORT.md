# P4.0 — Native Transport + Session Activation — Relatório

**Base:** `main` em `672ea99` · **Branch:** `claude/p4-0-native-transport-session`
**Decisão:** D-PROD-24 · **Estado:** implementada, em PR draft

## 1. Por que esta fatia existe antes de Setor

A P3 entregou um backend que sabe autenticar. O frontend continuou autenticando
na Base44. Entre os dois não havia nada: nem URL configurada, nem cliente HTTP,
nem sessão própria, nem catálogo de erro compartilhado.

Enquanto isso durar, **nenhuma capacidade pode ser considerada migrada** — o
navegador não tem como provar quem é para o backend próprio. Criar `Setor` no
Prisma antes disso produziria persistência que ninguém consegue consumir, e a
primeira tentativa de consumo descobriria, tarde, que faltavam quatro camadas.

A ordem é estrutural, não preferência: **P4.0 → P4.1 (Setor) → P4.2
(AreaPastagem)**, porque `AreaPastagem` depende de `Setor` e `Setor` depende de
existir caminho autenticado.

## 3. O caminho, ponta a ponta

```
navegador
   ↓  VITE_MAIKE_API_URL          (referência estática, sem override)
nativeHttpClient                  (única porta; anexa o Bearer)
   ↓  Authorization: Bearer <JWT MAIKE>
Fastify + @fastify/cors           (allowlist exata)
   ↓  jwtVerify
auth_context                      (tenant vem daqui, de lugar nenhum mais)
```

Sem token da Base44, sem `cliente_id` vindo do cliente, sem segredo no
frontend, sem CORS aberto, sem fallback silencioso.

## 4. As quatro decisões que valem explicação

### O login não manda `cliente_id`, e isso é a tenancy inteira

O corpo é exatamente `{cliente, login, senha}`. `cliente` é o código operacional
digitado por quem entra; `cliente_id` é o que o backend **devolve** depois de
autenticar. Essa inversão é o que impede o tenant de vir do payload.

O backend já recusa `cliente_id` no corpo com 400 — correção da P3. Mas não é
por isso que não mandamos: não mandamos porque o tenant não é nosso para
informar.

### A mensagem do servidor é descartada

O backend responde `{code, message, request_id}`. Usamos `code` e jogamos
`message` fora. Mensagem de servidor carrega caminho, id interno, fragmento de
query e, num dia ruim, eco da entrada do atacante — exibi-la daria aparência
confiável a texto não controlado, o mesmo defeito que a P1.1-R2 corrigiu.

P4T-10 prova isso com uma mensagem hostil de propósito, contendo URL,
`Authorization`, `Bearer` e SQL. Nenhum fragmento chega ao texto exibível.

### Não existe dual-auth

Se o backend MAIKE não responde, o usuário vê falha de login — não uma sessão
Base44 de consolação. Fallback transformaria "o backend caiu" em "sua senha está
errada", que manda o usuário tentar para sempre e esconde o incidente de quem
poderia resolvê-lo. AUTH11 fixa a ausência.

### `sessionStorage` não resolve XSS, e o relatório não vai fingir que resolve

O JWT fica em memória mais `sessionStorage`, numa chave única. `localStorage`
sobrevive a fechar o navegador e deixaria sessão aberta para o próximo usuário
da máquina.

Mas `sessionStorage` é acessível a JavaScript: um XSS nesta origem lê o token.
A troca **reduz a janela, não a classe do problema**. Defesa real é cookie
`HttpOnly` com `SameSite`, refresh com rotação, revogação no servidor e CSP —
nada disso está nesta fatia, e pertence à P8. Registrado em D-PROD-24, item F.

## 5. CORS — a regra e o erro que ela evita

`FRONTEND_ORIGINS` é lista de origins exatas, comparadas por igualdade.

O erro clássico é `startsWith`. P4B-03 exercita exatamente o que ele deixaria
passar:

| Permitida | Impostor | `startsWith` | Real |
|---|---|---|---|
| `https://maike.app` | `https://maike.app.evil.com` | passaria | **recusa** ✅ |
| `https://maike.app` | `https://maike.appevil.com` | passaria | **recusa** ✅ |
| `https://maike.app` | `http://maike.app` | — | **recusa** ✅ |
| `https://maike.app` | `https://maike.app:8443` | — | **recusa** ✅ |

Lista vazia = nenhuma origin autorizada. Configuração ausente vira porta
fechada, nunca aberta.

Requisição sem `Origin` passa: CORS é proteção que o **navegador** aplica a
páginas web. Recusá-la não bloquearia atacante nenhum — quem controla o cliente
controla o header — e quebraria health check e integração. A defesa dessas
chamadas é o JWT.

## 6. Bootstrap local — o que ele não é

`npm run auth:bootstrap:local` cria o primeiro Cliente + Usuario. Existe porque
a P3 ensinou o backend a autenticar e não criou forma de existir um usuário: sem
isso, a P4.0 seria inverificável.

É script, não endpoint, porque endpoint de bootstrap é porta permanente de
criação de conta com privilégio, que nasce "temporária" e sobrevive a todas as
fases. Gestão de usuários é da P6.

Proteções: recusa `NODE_ENV=production`; exige as cinco variáveis sem padrão
para nenhuma — não existe usuário `admin` com senha `admin` esperando alguém
esquecer de trocar; **falha se a conta já existir** em vez de sobrescrever (um
bootstrap que redefine senha é tomada de conta com nome amigável); não imprime
senha, hash, id nem `DATABASE_URL`; não fornece `id` — quem produz é o
`@default(cuid())`, como verifica `P3-TEN-RUNTIME-IDENTITY`.

> A primeira versão de duas regras **reprovou o próprio repositório**.

> uso. E `Authorization` casava no `base44Provider.js`, que monta esse cabeçalho

legítimo). A correção foi tornar a regra **precisa**, não afrouxá-la: a
verificação passou a ser sobre a *posição* — quem consome a URL, quem lê o
**token nativo** — em vez de sobre a palavra. NAT-14 e NAT-15 são os controles
positivos que quebram se alguém alargar de volta.

## 8. Duas correções que os testes obrigaram

Nenhuma das duas era bug de fixture.

**A guarda do token estava na camada errada.** Eu a coloquei em
`src/apis/session/`, e dois testes de arquitetura reprovaram: `src/apis/**` não
pode tocar armazenamento do navegador (B10), e `_core` alcançando o interior de
outro módulo de API é bypass de camada (B13). As duas regras estavam certas.
O arquivo foi para `src/lib/auth/`, onde as preocupações de ambiente vivem —
como `src/lib/offline/`. **A regra não foi afrouxada para acomodar o arquivo.**

**A sessão lia o valor do token sem precisar dele.** `nativeSessionApi` chamava
`getNativeToken()` só para saber se havia sessão. Isso fazia
`P4-NATIVE-HTTP-BOUNDARY` reprovar — corretamente. A correção foi no código, não
no gate: a API passou a usar `hasNativeToken()`, presença em vez de valor. Agora
"só o cliente HTTP lê o token" é literalmente verdade e verificável.

# 19. P4.0-R1 — Semântica de restauração de sessão

## 19.1 O que a auditoria encontrou

A auditoria externa do HEAD `0185d10` — com CI verde, 19/19 — encontrou um
bloqueador que nenhum gate e nenhum teste meu tinha pegado.

`restaurarSessao()` apagava o JWT para **qualquer** erro:

```js
} catch (erro) {
  // Token recusado sai de cena. Falha de rede também limpa: sem confirmação
  // não há sessão, e o caminho de volta é o login — não um estado "talvez
  // autenticado" que a tela não sabe representar.
  clearNativeToken();
  return { autenticado: false, contexto: null };
}
```

O comentário é meu, e é a parte que mais incomoda. Eu não esqueci de tratar o
caso: eu **raciocinei até a decisão errada e a documentei**, o que a fez parecer
deliberada e correta para qualquer leitor seguinte — inclusive para mim, ao
reler.

## 19.2 O impacto

Rede caída, timeout, CORS recusado e 500 do servidor viravam
`{autenticado: false}` — **indistinguível de "sua credencial foi recusada"**.

Na prática: um backend fora do ar por trinta segundos destruía a sessão de quem
estava trabalhando, mostrava o formulário de login como se a senha estivesse
errada, e apagava a única credencial que o usuário tinha. Ele então digitaria a
senha, que também falharia — porque o servidor continuava fora do ar.

A regra que faltava, em uma linha: **falha de autenticação não é falha de
disponibilidade.**

## 19.3 O contrato novo

| Resposta | Token | Estado | Tela |
|---|---|---|---|
| 200, contexto válido | preservado | `autenticada` | aplicativo |
| `TENANT_CONTEXT_REQUIRED` | **removido** | `nao_autenticada` | login nativo |
| rede · timeout · CORS · 5xx | **preservado** | `validacao_indisponivel` | "Não foi possível validar sua sessão" + *Tentar novamente* |

A separação é por **código**, não por faixa de status: `TENANT_SCOPE_VIOLATION`
(403) não afirma que a credencial é inválida, e por isso também não limpa o
token (P4R1-T03c).

Na indisponibilidade a função **lança** em vez de devolver veredito. Devolver
`{autenticado: false}` seria continuar mentindo, só que sem apagar o token: o
chamador ainda leria como logout. A camada de cima precisa distinguir "não
consegui validar" de "validei e foi recusada".

**Isto não é confiar no token guardado.** Enquanto o backend não confirmar,
`isAuthenticated` continua `false` e o aplicativo continua fechado. É
**fail-closed sem destruir a credencial**.

## 19.4 O estado que faltava

`AuthContext` passou a ter quatro estados discriminados, porque o quarto não era
representável por dois booleanos:

```
CARREGANDO · AUTENTICADA · NAO_AUTENTICADA · VALIDACAO_INDISPONIVEL
```

Com `isAuthenticated: false` e `isLoadingAuth: false`, a única leitura possível
era "deslogado" — e foi exatamente assim que indisponibilidade virou pedido de
senha. `isAuthenticated` e `isLoadingAuth` continuam existindo, agora
**derivados** do estado, nunca guardados em paralelo.

`revalidarSessao()` repete a validação com o **mesmo** token. Nunca chama
`/auth/login`, nunca pede senha, nunca decodifica o JWT no frontend.

## 19.5 A tela

`src/components/auth/NativeSessionUnavailable.jsx`. Durante o outage o `App`
não renderiza **nem** o login **nem** o conteúdo protegido — as duas ausências
são o ponto, e P4R1-T06 prova as duas. O texto vem do catálogo público via
`getApiErrorMessage`; nada de status cru, URL, `request_id` ou mensagem do
servidor.

A ordem dos ramos no `App` é o contrato:

```
1. carregando            → ainda não sabemos nada
2. validação indisponível → não sabemos, e não é culpa do usuário
3. não autenticado        → sabemos: precisa entrar
4. autenticado            → aplicativo
```

O segundo ramo é o que faltava. Sem ele, "não sabemos" caía no terceiro.
