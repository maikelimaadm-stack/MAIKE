## 1. A causa técnica

A R3 tinha duas funções com semânticas diferentes:

```js
origemProvider(expr)    // usada para CLASSIFICAR um binding local
entregaProvider(expr)   // usada para VERIFICAR um export
```

`entregaProvider` era mais ampla — reconhecia contêiner, função, array. Mas a
passada de propagação só adicionava um nome ao conjunto quando o initializer era
**origem direta**:

```js
if (!origemProvider(node.initializer, origens, rel)) return;
```

E o `export { nome }` verificava apenas `origens.has(nome)`.

O resultado é uma assimetria pura: a **mesma** capacidade reprovava quando
declarada com `export` embutido e passava quando declaração e export eram
separados por uma linha.

```js
export const bag = { empresaProvider };            // reprovava
const bag = { empresaProvider }; export { bag };   // passava
```

Medi as 19 formas desta missão contra o HEAD de entrada antes de escrever
qualquer correção: **15 passavam indevidamente**. A CI verde da R3 era real e
não provava a separação declaração/export.

## 2. R4-B1 — contêiner local exportado depois

```js
const bag = { empresaProvider };            export { bag };
const bag = [empresaProvider];              export { bag };
const bag = { create: empresaProvider.create };  export default bag;
const bag = { ...empresaProvider };         export { bag as providerBag };
```

Todas reprovam agora. O consumidor que recebe `bag` recebe o provider.

## 3. R4-B2 — função local exportada depois

```js
const getProvider = () => empresaProvider;  export { getProvider };
const getCreate = () => empresaProvider.create;  export default getCreate;
function getProvider() { return empresaProvider; }  export { getProvider };
```

Uma função que entrega capacidade é, ela própria, capacidade. `FunctionDeclaration`
precisou de tratamento próprio: não é `VariableDeclaration`, então a propagação
passou a classificar também o nome da função pelo que o corpo devolve.

Continua passando, porque devolve o **resultado** da operação:

```js
const createEmpresa = (dados) => empresaProvider.create(dados);  export { createEmpresa };
```

## 4. R4-B3 — alias de contêiner ou função

```js
const bag = { empresaProvider };  const alias = bag;  export { alias };
const getProvider = () => empresaProvider;  const alias = getProvider;  export { alias };
const operations = { create: empresaProvider.create };
const a = operations;  const b = a;  export default b;
```

Tudo no mesmo arquivo, em bindings locais, sem chamada externa e sem passagem por
parâmetro entre módulos. Não é análise interprocedural, e não foi empurrado para
DBT-18.

## 5. R4-B4 — o ponto fixo tinha escape silencioso

A R3 usava `for (let volta = 0; volta < 8; volta += 1)` com `break` quando o
conjunto parava de crescer. O comentário e o relatório descreviam um ponto fixo
que termina por finitude — mas o código tinha um teto arbitrário que **saía em
silêncio**.

Isso não era teórico. Medi:

```
cadeia de 12 aliases em ordem direta   → detectada  (uma volta basta)
cadeia de 12 aliases em ordem INVERSA  → NÃO detectada
```

Em ordem direta, uma única varredura já propaga tudo, porque cada declaração já
encontra a anterior classificada. Em ordem inversa é preciso uma volta por elo —
e na nona o laço desistia sem dizer nada. Um limite que sai calado transforma
"não consegui analisar" em "está tudo certo".

Agora é ponto fixo real: `while (cresceu)`, sem teto. A terminação vem da
monotonicidade — cada volta só adiciona nomes já presentes no AST, e o arquivo
tem um número finito de identificadores. A guarda residual (`declaracoes.length + 2`)
existe apenas contra um bug futuro que quebre a monotonicidade, e **lança**:

```js
throw new Error(`api-boundary: ponto fixo não convergiu em ${rel} …`);
```

Nunca devolve resultado parcial. Há teste com cadeia invertida de 40 elos.

## 6. R4-B5 — expressões de controle local

O `Block` era percorrido só no primeiro nível de `statements` procurando
`ReturnStatement`. Ficavam de fora `if`, `switch`, `try`, `for` e blocos
aninhados. E ternário e curto-circuito não eram tratados.

```js
export const getProvider = (c) => (c ? empresaProvider : null);   // reprova
export const getProvider = (c) => c && empresaProvider;           // reprova
export function getProvider(c) { if (c) return empresaProvider; return null; }  // reprova
export function getProvider(v) { switch (v) { case 'p': return empresaProvider; default: return null; } }  // reprova
```

`corpoEntregaCapacidade()` percorre o corpo em qualquer profundidade e **para em
fronteiras de escopo** — função ou classe aninhada. O `return` de uma função
interna pertence a ela, não a esta; se a interna for devolvida, a própria
expressão de retorno já é classificada. Sem esse corte, isto viraria falso
positivo:

```js
export function g() { const interna = () => empresaProvider; return 1; }  // passa
```

O gate não interpreta a condição do ternário: se **existe** caminho que devolve
capacidade, o export entrega capacidade.

## 7. R4-B6 — `.bind()` é capacidade, não dado

A regra "qualquer `CallExpression` devolve resultado" tinha uma exceção real:

```js
export const createRaw = empresaProvider.create.bind(empresaProvider);   // reprova
const createRaw = empresaProvider.create.bind(empresaProvider); export { createRaw };  // reprova
```

`bind()` devolve uma **função chamável** que ainda executa a operação — fora de
`runProviderCall`, da normalização de erro, da validação de argumento e do
contrato público. É capacidade com outro nome.

`.call` e `.apply` executam a operação ali mesmo e devolvem o resultado, então
continuam passando. Há teste positivo para os dois.

## 8. R4-B7 — o comentário técnico falso

O comentário de `scriptKindOf()` ainda afirmava que `ScriptKind.JS` fazia
`import x = require(…)` "não virar nó algum". A própria R3 mediu e registrou o
contrário — o parser do TypeScript é tolerante e produz
`ImportEqualsDeclaration` sob ambos os `ScriptKind`. O código contradizia o
relatório, o commit funcional e a evidência de teste.

O comentário foi reescrito com a razão verdadeira: manter o AST coerente com o
arquivo real, porque `.tsx` lido como `TS` produz erro de parse, e não depender
da tolerância acidental do parser. E registra corretamente que o que faltava
para `import equals` era **coletar o binding** do nó, que existia e era ignorado.

Nenhum teste foi alterado para esconder a contradição. Ao contrário: LW18 inclui
um teste que **exercita** a tolerância do parser, para que a afirmação do
comentário falhe visivelmente se o TypeScript mudar de comportamento, em vez de
virar folclore.

## 9. O modelo final de proveniência

A assimetria foi eliminada na raiz: existe **uma** função, `ehCapacidade()`, e
tanto a classificação de binding quanto a verificação de export chamam ela.
`entregaProvider()` permanece como alias por legibilidade.

Um binding local é **capacidade** quando seu initializer é:

| Forma | Exemplo |
|---|---|
| origem do provider | `empresaProvider`, `import('…/_providers/…')`, `require(…)` |
| membro derivado de origem | `providers.empresaProvider`, `empresaProvider.create` |
| contêiner que a contenha | `{ p }`, `[p]`, `{ ...p }`, `{ create: p.create }` |
| função que a devolva | `() => p`, `function f() { return p }` |
| `.bind()` de método derivado | `p.create.bind(p)` |
| alias de binding já classificado | `const a = bag` |
| ternário ou curto-circuito com ramo que a devolva | `c ? p : null`, `c && p` |

**Não** é capacidade quando o initializer chama a operação e devolve o
resultado — `p.create(d)`, `await p.list(x)`, `p.create.call(p, d)` — ou quando é
um contêiner só com resultados já materializados.

A propriedade que fecha a missão, escrita como teste:

```
declarar-e-exportar  ≡  exportar-na-declaração
```

Há um teste que roda as duas formas de quatro códigos diferentes e exige
classificação idêntica.

**Escalabilidade:** nada no analisador cita `empresa`. `moduleOf()` e
`moduleTargetedBy()` derivam o módulo do caminho, então `lote`, `mapa`, `setor` e
`manejo` já nascem cobertos.
