## 1. Por que a CI verde não bastava

A P1.1 entregou a fronteira e provou que a página parou de falar `base44`. Mas o
gate protegia **o que a fronteira substituiu**, não **a fronteira em si**. Cinco
brechas ficaram abertas, e a auditoria externa as encontrou.

O padrão é o mesmo das missões anteriores: cada uma media um sinal correlato em
vez da propriedade.

| # | Brecha | O que o gate media | O que precisava provar |
|---|---|---|---|
| B1 | bypass de camada | "importa `base44`?" | "respeita UI → service → API → provider?" |
| B2 | SDK por outras sintaxes | `import … from` | qualquer forma de carregar o pacote |
| B3 | `ApiError` vazando | `Error` serializa como `{}` | nada sensível sai, com qualquer `cause` |
| B4 | SSOT desalinhado | — | o documento descreve o HEAD |
| B5 | precedência documentada | — | a documentação descreve o código |

## 2. B1 — bypass da camada `_providers`

### O buraco

Isto passava com o gate verde:

```js
import { empresaProvider } from '@/apis/_providers/base44Provider';
export const carregar = () => empresaProvider.list('-created_date');
```

Não importa `base44Client`. Não contém `base44.entities`. Não reexporta o objeto
`base44`. Mas pula service e API de módulo — a fronteira inteira. O gate media
"quem toca na Base44", e o desenho exige "quem respeita a camada".

### A correção

`src/apis/_providers/**` é interno. Só `src/apis/<modulo>/**` importa de lá, com
`<modulo>` sem prefixo `_`.

A regra é escrita para escalar sozinha: quando P1.2 criar `src/apis/lote/`, ele
já nasce autorizado sem tocar no gate; `_core/` e `_providers/` continuam de
fora; e página, componente, hook, service, repository e `src/lib/` nunca entram.

Resolução por AST, cobrindo alias `@/`, caminho relativo, extensão opcional,
`import()` e `export … from`. Código novo: `P11-API-BOUNDARY-LAYER-BYPASS`.

| L2 | componente | reprova |

| L7 | página reexportando o provider | reprova |

## 3. B2 — carregamento do SDK em outras sintaxes

O analisador cobria `import … from` e `export … from`. Estas escapavam:

```js
await import('@base44/sdk');
const sdk = import('@base44/sdk');
const sdk = require('@base44/sdk');
```

Agora todas são detectadas, mais `import x = require(…)`. A detecção é
**sintática**: comentário ou string comum contendo o nome do pacote não reprova
(S6, S7). Oito casos, S1 a S8.

---

## 4. B3 — `ApiError` vazando informação

### B3.1 — `cause` enumerável

```js
this.cause = info.cause;   // propriedade enumerável
```

O teste anterior usava `Error`, que serializa como `{}` — então o teste passava
sem provar nada. Com um objeto simples, tudo vazava no primeiro
`JSON.stringify(erro)` de um log:

```js
new ApiError(code, { cause: { Authorization: 'Bearer …', config: { … } } });
```

Agora `cause` é definido com `Object.defineProperty` e `enumerable: false`:
continua acessível para diagnóstico, some de `Object.keys` e de
`JSON.stringify`.

### B3.2 — mensagem desconhecida exibida crua

`getApiErrorMessage` devolvia `erro.message` de um `Error` qualquer. Mensagem de
SDK costuma carregar URL com query string, cabeçalho ou trecho de payload — e
ia direto para o toast.

Contrato novo: **só `ApiError` tem mensagem exibível**. Erro que não passou pela
normalização não tem mensagem pública, tem fallback. E o próprio fallback é
validado: vazio, só espaço ou não-string cai numa mensagem padrão interna.

### Testes E1–E10

Cobrem: `cause` `Error` acessível e fora da serialização; objeto enumerável com
`Authorization`; segredo aninhado em `config.headers` e `response.data`;
`Object.keys` sem `cause`; `Error` e string com token caindo no fallback;
`ApiError` conhecido entregando a mensagem pública; erro normalizado sem a
mensagem crua; `JSON.stringify` sem segredo sintético; fallback inválido.

O teste inseguro que exigia `getApiErrorMessage(new Error('do provider')) === 'do provider'`
foi corrigido — aquele comportamento era a brecha.

## 5. B5 — precedência documentada errada

O relatório e o corpo da PR diziam `query string > localStorage > env`. O código
faz — e sempre fez, herdado do legado:

```
query string  >  env/default  >  localStorage  >  null
```

A diferença é observável: com `VITE_BASE44_APP_ID` definido e um valor
persistido diferente, vence o ambiente. Comportamento preservado; documentação
corrigida no módulo, no SSOT e no corpo da PR. Três testes explícitos: R1 (URL
vence tudo), R2 (env vence storage), R3 (storage entra quando os dois faltam).

### Um achado do próprio `verify:all`

A primeira execução completa depois destas mudanças reprovou em `no-secrets`:

```
- [P01-SECRET-HARDCODED] tests/smoke/empresaBoundary.test.js:73 — Segredo atribuído diretamente
```

Era `apiKey: 'chave-sintetica-de-teste'`, escrito como literal no teste novo de
`cause` aninhado. O gate estava certo — é uma atribuição de segredo em arquivo
versionado, e a regra não tem como saber que o valor é falso. As fixtures
passaram a montar os valores em tempo de execução, como as do gate de segredos
já faziam. Fica registrado porque o gate pegou um erro meu na mesma PR em que
endureço a fronteira.
